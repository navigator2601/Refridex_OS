# Архітектурний регламент та інструкція розробки Refridex OS

Цей документ є головним технічним регламентом та покроковою інструкцією для розробки, масштабування та підтримки системи **Refridex OS**.

---

## 🧭 Покроковий план розробки

### Етап 1. Архітектурне планування та конфігурація середовища
1. **Ізоляція оточення та фіксація залежностей:**
   - Формування `requirements.txt`:
     ```txt
     aiogram>=3.0.0
     telethon
     asyncpg
     pydantic>=2.0
     python-dotenv
     aiofiles
     ```
   - Налаштування `.env` та централізованого об'єкта конфігурації `config.py` (токен бота, `DATABASE_URL` для PostgreSQL, `API_ID`, `API_HASH` для MTProto-клієнта Telethon, `ADMIN_ID`).
2. **Проєктування модульної структури проєкту:**
   - `database/` — пули з'єднань, моделі та SQL-репозиторії.
   - `handlers/` — роутери команд, reply- та inline-кнопок.
   - `keyboards/` — динамічні конструктори клавіатур.
   - `middlewares/` — RBAC (контроль доступу) та прокидання сесій БД.
   - `services/` — парсер заявок, калькуляція матеріалів, генератор звітів.
   - `telegram_client_module/` — підключення та керування Telethon-клієнтами.
3. **Пул підключень до БД:**
   - Створення асинхронного менеджера підключень `database/db_pool_manager.py` через `asyncpg.create_pool()`.
   - Реєстрація `DbSessionMiddleware`, що прокидає пул або екземпляр з'єднання в кожен обробник події `aiogram`.

---

### Етап 2. Рівні доступу (RBAC) та динамічна система меню
1. **Модель користувача та права в БД:**
   - Використання схеми `telethon_auth.users`:
     - `id` (Telegram User ID);
     - `access_level`:
       - `0` — Гість / Монтажник;
       - `1` — Бригадир / Диспетчер;
       - `2` — Адміністратор;
     - Прапорці прав: `can_manage_sessions`, `can_manage_chats`, `can_manage_users`.
2. **Middleware контролю доступу:**
   - Реалізація фільтра/мідлварі, яка перехоплює вхідний `event.from_user.id`, перевіряє статус у таблиці `telethon_auth.users` та передає об'єкт користувача з його `access_level` у контекст хендлера.
3. **Динамічна Reply-клавіатура:**
   - Реалізація фабрики головного меню в `keyboards/reply_keyboard.py`.
   - Фільтрація кнопок за правилом: `access_level >= min_level`:
     - Базові інструкції та введення замірів доступні всім;
     - Пошук по всіх ТТ, вивантаження та звірка — вищим рівням;
     - Керування сесіями Telethon та адміністрування — лише рівню Admin.
   - Впровадження пагінації (розбиття на сторінки через `BUTTONS_PER_PAGE`), якщо список доступних кнопок перевищує заданий ліміт.
4. **Контекстні Inline-клавіатури:**
   - Розробка інлайн-кнопок для навігації всередині сутностей: перемикання між кондиціонерами об'єкта (К1, К2...), швидкі дії:
     - `➕ Додати пайку`
     - `📍 Маршрут Google Maps`
     - `✅ Сформувати підсумок`

---

### Етап 3. Модуль читання та парсингу повідомлень із груп (Telethon + Pipeline)
1. **Інтеграція клієнта Telethon:**
   - Авторизація клієнта MTProto через збережені в базі сесії (`telethon_auth.sessions`).
   - Створення сервісу зчитування повідомлень за вказаний період або певної кількості останніх постів із цільових чатів (довідник `telethon_auth.allowed_chats`).
2. **Парсинг та структурування заявок:**
   - Реалізація обробника вхідного тексту: вилучення коду ТТ (нормалізація до формату «А3406»), геокоординат, діапазону дат та переліку обладнання (наприклад: `4\24н` і `1\12н`).
   - Валідація результату через модель Pydantic (`InboundStoreTask`): перевірка меж координат України (Geo-Fence), очищення текстових коментарів адреси (поверх, цоколь тощо).
3. **Збереження фундаменту завдань у PostgreSQL:**
   - Синхронізація точки в `stores.outlets` та `stores.addresses`.
   - Створення завдання в `montage.tasks` зі статусом `PLANNED`.
   - Автоматична генерація чернеток блоків у `montage.draft_measurements`: якщо розпарсено `4×24н` та `1×12н`, у базі одразу ініціалізуються рядки для К1–К4 (24Н) та К5 (12Н), позбавляючи монтажника необхідності ручного введення.

---

### Етап 4. Інтерфейс монтажника (Введення замірів та робота з БД)
1. **FSM (Finite State Machine) для обліку монтажу:**
   - Створення машини станів `MontageStates`:
     `Вибір активної ТТ` $\rightarrow$ `Вибір блоку К1..Кn` $\rightarrow$ `Введення відрізків траси`.
2. **Обробка формул замірів:**
   - Створення парсера арифметичних виразів: прийом повідомлень виду `130+340+530` безпосередньо з чату.
   - Автоматичне конвертування суми сантиметрів у метри ($1000\text{ см} \rightarrow 10.0\text{ м}$) та фіксація точок пайок на магістралі.
   - Збереження проміжних даних у `montage.draft_measurements` (захист від втрати даних при розриві інтернет-з'єднання чи сесії).
3. **Розрахункове ядро:**
   - Автоматичний розрахунок перевищення базової довжини траси з наявної специфікації кондиціонера.
   - Калькуляція необхідної дозаправки фреону в грамах за формулою перевищення довжини.

---

### Етап 5. Генерація та адресне відправлення звітів у вибрані групи
1. **Агрегація даних:**
   - Складання єдиного оптимізованого SQL-запиту, що об'єднує:
     - Дані торгової точки (ТТ);
     - Фактично виконані заміри по кожному блоку (К1–Кn);
     - Сумарну кількість витрачених матеріалів та пайок;
     - Нормативні параметри пусконалагодження.
2. **Форматування підсумкової картки:**
   - Збирання структурованого HTML-повідомлення зі зведенням виконаних робіт, посиланнями на локацію (Google Maps) та підсумковим кілометражем і матеріалами.
3. **Диспетчеризація відправлення в робочі групи:**
   - Інтерфейс для вибору цільової групи зі списку `allowed_chats` за допомогою динамічної Inline-клавіатури.
   - Виклик методу `bot.send_message(chat_id=selected_group_id, text=report_text, parse_mode=ParseMode.HTML)` з надійною обробкою винятків (відсутність прав, блокування ботом).

---

### Етап 6. Логування, тестування та підготовка до експлуатації
1. **Асинхронне логування та аудит:**
   - Налаштування `utils/logger.py` з ротацією логів: фіксація помилок парсингу, дій монтажників та змін рівнів доступу.
2. **Обробка виняткових ситуацій:**
   - Захист від втрати з'єднання з базою PostgreSQL/Neon (автоматичний SSL reconnection).
   - Запобігання конфлікту `TelegramConflictError` при паралельних перезапусках процесу бота.
3. **Розгортання та стійкість:**
   - Організація фонового воркера (Background Worker) для безперервного Polling або переведення на Webhook у разі масштабування навантаження.
